How a chunk becomes a mesh

The old process, the two changes made to it, and why the new one is about 11× faster while producing exactly the same triangles. Code: src/voxel/greedy_meshing.rs and src/voxel/chunk_loading.rs.

The goal of meshing. A chunk is 32×32×32 voxels. The GPU doesn't draw voxels; it draws triangles. So for every chunk we must answer:
  1. Which faces are visible? A voxel face is only drawn if the neighbor on that side doesn't cover it (stone next to stone = hidden).
  2. How few rectangles can cover those faces? "Greedy meshing" merges neighbouring faces of the same material into one big rectangle (a quad = 2 triangles).
Both versions answer the same two questions. They only differ in where they run and how they compute it.

1. Where the work runs (step 1)

Every chunk needs up to three meshes: collider (physics), opaque (what you see), water (translucent). The collider was already built on a background thread. The visible meshes were not, because they need to look at neighbouring chunks, and neighbours live in the ECS (ChunkMap + Query<&BaseChunk>), which only the main thread can read.

The trick: copy just the border, not the whole neighbour

To decide if a face on the edge of the chunk is visible, the mesher only ever looks one voxel past the edge. So instead of giving the background thread access to the whole world, we copy the single 32×32 layer of each of the 6 neighbours that touches our chunk. That's NeighborBorders:

pub struct NeighborBorders([Option<Box<[VoxelType]>>; 6]);
//                          ^ one slot per face: -X +X -Y +Y -Z +Z
//                            None = neighbour not loaded yet ("unknown")

NeighborBorders::gather does 6 hash-map lookups (one per neighbour) and copies 6 KB. The old code did a hash-map lookup + ECS query for every border cell: about 6 × 1024 lookups per mesh.

The flow in chunk_loading.rs is now:

  1. complete_chunk_generation_system: voxels + collider are ready → gather borders, clone the chunk, spawn a ChunkMeshTask. Insert BaseChunk immediately so chunks finishing later can see this one as a neighbour.
  2. complete_chunk_mesh_system: when the task is done → insert Mesh3d, material, water child.
Three side effects this needed handling for:
  • No holes: the far LOD backdrop is only removed when the real chunk has a mesh (Without<ChunkMeshTask> in retire_covered_lods_system), not merely when it has voxels.
  • No stale mesh: if you break a block in a chunk whose first mesh is still in flight, the remesh waits (Without<ChunkMeshTask> in remesh_dirty_chunks_system). Otherwise the older in-flight mesh would land afterwards and undo your edit.
  • Same neighbour semantics: None in a border slot behaves exactly like "neighbour not loaded" did before: opaque draws the face, water skips it.

2. The old mesher: one cell at a time

For each axis (X, Y, Z), each depth d (0–31), and each direction (+, −), it built a slice: 3 × 32 × 2 = 192 slices. For each slice:

// generate_slice_mask: 1024 cells, each one checked separately
for j in 0..32 { for i in 0..32 {
    let me       = chunk.voxel_types[x][y][z];
    let neighbor = chunk.voxel_types[x+dx][y+dy][z+dz]; // or a cross-chunk lookup
    mask[i + j*32] = if in_layer(me) && !hides(neighbor) { Some(me) } else { None };
}}
// greedy_mesh_slice: walk the mask, grow rectangles, mark a `processed` Vec<bool>

That's ~197,000 cell checks, 384 heap allocations (a mask + a processed vec per slice), and ~6,000 cross-chunk lookups per mesh, even when most of the chunk is solid stone or empty air.

3. The new mesher: 32 voxels at once (step 2)

A chunk is exactly 32 wide, and a u32 has exactly 32 bits. So a whole column of voxels along one axis fits in one integer: bit k = 1 means "cell k is solid". Comparing a column with its neighbour then becomes a single shift + AND for all 32 cells at once.

3a. Two bitsets per column

build_axis_columns reads the chunk once and fills, for each of the 3 axes and each of the 32×32 columns:

  • in_layer: u32: cell belongs to the mesh we're building (e.g. solid, not water).
  • hidden: u64: cell covers a neighbouring face. It holds 34 bits: the 32 cells shifted up by one, plus the neighbour chunk's border cell at bit 0 (the −side) and bit 33 (the +side). This padding is why the chunk edge needs no special case.

Then the visible faces for a whole column:

// cell k's neighbour at k+1 lives at bit (k+1)+1 → shift by 2
faces_plus  = in_layer & !((hidden >> 2) as u32);
// cell k's neighbour at k-1 lives at bit (k-1)+1 = k → no shift
faces_minus = in_layer & !(hidden as u32);

3b. Split faces by material into binary planes

The bit trick tells us that a face exists, not which material it is, and we must never merge stone with dirt (different colour). So collect_face_planes walks each set bit (trailing_zeros jumps straight to it; empty air costs nothing) and drops it into a plane for its (depth, material): 32 rows of u32, where row j, bit i = "there is a face at (i, j)". A small used bitmask remembers which planes got anything, so empty ones are skipped.

3c. Greedy merge with bit operations

greedy_mesh_plane works on one material's plane:

let i     = plane[j].trailing_zeros();          // first face in the row
let width = (plane[j] >> i).trailing_ones();    // how many in a row
let run   = (u32::MAX >> (32 - width)) << i;     // bitmask of that run
plane[j] &= !run;                               // consume it
while plane[j + h] & run == run {               // next row has the same run?
    plane[j + h] &= !run; h += 1;               //   → grow the quad downwards
}

Clearing bits replaces the old processed array: a consumed face simply isn't in the plane any more. The plane ends empty, so it's reused for the next axis without clearing.

4. What did not change

  • add_greedy_quad: vertex positions, normals, per-quad colour (voxel_color sampled at the cell centre), face shading, winding.
  • Layer rules: cell_in_layer, face_hidden_by (water is hidden by anything non-air), face_visible_against_unknown.
  • Grass tops (Y+) are still never merged: each gets its own 1×1 quad for its own baked colour.
  • The quad scan order inside one material is the same (row by row, grow along U first, then V), which is why the rectangles come out identical.

5. How it was verified

Before deleting the old mesher, a temporary test ran both on real generated chunks and compared every quad bit-for-bit (positions, normals, colours, index winding):
